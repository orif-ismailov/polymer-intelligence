# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Polymer Intelligence — платформа рыночной аналитики полимеров Узбекистана

Версия 1.0 · 12.06.2026 · Статус: на согласование

---

## 1. Цель проекта

Единая система сбора, структурирования и доставки рыночной информации по полимерам внутреннего рынка Узбекистана:

- **Внутренний дашборд** — терминал для команды: лента рынка, заявки, цены, контрагенты, алерты.
- **Telegram Web App** — клиентский интерфейс подачи заявок на закупку и получения рыночной информации.
- **Telegram-бот** — слой уведомлений (алерты команде, статусы заявок клиентам, запуск Web App).
- **Telegram-канал** — автоматизированная публикация рыночных отчётов (с ручным подтверждением).
- **Движок сбора данных** — парсинг UZEX, мониторинг Telegram-каналов, приём заявок.

Все компоненты работают на одном backend и одной базе данных (см. приложение «Архитектура БД», документ polymer-intelligence-db-architecture.md — является неотъемлемой частью настоящего ТЗ).

### 1.1. Что система ДЕЛАЕТ и НЕ ДЕЛАЕТ (зафиксировать с заказчиком)

Система **отслеживает** рыночные события, **структурирует** их и **объясняет** движения цен наблюдаемыми факторами (включая внешний фон с Фазы 2).

Система **не прогнозирует** цены, **не даёт** торговых рекомендаций и **не гарантирует** полноту охвата рынка. AI-оценки (lead score, классификация срочности) являются вспомогательными и могут содержать ошибки; финальное решение принимает человек.

### 2.3. Зафиксированные допущения (изменение = изменение скоупа и оценки)

1. **Ответ клиенту на заявку** выполняется менеджером вручную через Telegram. Система фиксирует только смену статуса заявки. Внутренний модуль «офферы клиентам» — вне скоупа.
2. **Файлы заявок** хранятся как telegram_file_id; скачивание в хранилище — при первом открытии менеджером.
3. **Отчёты** в Фазах 1–2 генерируются на русском языке. Узбекская версия — отдельная задача.
4. **Список Telegram-каналов** для мониторинга предоставляет заказчик (до 20 в Фазе 1). Добавление каналов сверх — поддержка, см. п. 8.
5. **Платные международные источники** (ChemOrbis, Argus, Platts, Polymerupdate, ETS) — вне скоупа полностью. См. п. 7.
6. **AI-аналитика уровня «hot buyers / циклы / аномалии»** (Фаза 3) не входит в настоящее ТЗ и оценивается отдельно после накопления ≥3 месяцев данных.
7. Дизайн принимается по предоставленным мокапам; новые экраны сверх перечисленных — изменение скоупа.
8. **ETS Kazakhstan:** биржа специализируется на агропродукции, нефтепродуктах, металлах и промтоварах; объём полимерных позиций в её публичных индикаторах на момент подписания неизвестен. Фаза 2 начинается с верификации; при отсутствии пригодных данных компонент исключается без пересмотра стоимости остального скоупа.
9. **Турция:** мониторинг ограничен публичными Telegram-каналами. Парсинг сайтов турецких трейдеров/портовых складов — отдельная оценка по конкретному списку URL от заказчика (каждый сайт = отдельный сборщик с отдельной поддержкой).
10. **SOCAR Polymer и аналогичные производители** публичных прайс-листов не публикуют; их мониторинг ограничен новостями в открытых источниках.
11. **Границы конструктора источников:** через админку без программирования подключаются публичные Telegram-каналы, публичные веб-страницы без авторизации и без JS-рендеринга, RSS-фиды и простые HTML-таблицы. Источники за логином, с защитой от ботов, со сложной динамической вёрсткой или нестандартными форматами подключаются разработчиком (типовой случай — до 1 рабочего дня в рамках поддержки). Качество AI-извлечения с произвольных страниц ниже, чем со специализированных парсеров, и под пороги п. 6.3 не подпадает.

### 2.4. Вне скоупа (явно)

- Прогнозирование цен, торговые рекомендации, скоринг кредитоспособности контрагентов.
- iOS/Android нативные приложения (только Telegram Web App).
- Интеграция с 1С, CRM, платёжными системами.
- Мониторинг закрытых (приватных) каналов и чатов без согласия владельцев.
- SLA на доступность внешних источников (UZEX, SunSirs, DCE, Telegram) — best effort.

## 3. Архитектура

```
                            ┌─────────────────────────────┐
  UZEX (HTML) ──scraper──►  │                             │ ──► Дашборд (React/Next.js)
  TG-каналы ──userbot────►  │  FastAPI + Celery + Redis   │ ──► Web App (React, TG SDK)
  SunSirs/DCE ──cron─────►  │  PostgreSQL 16              │ ──► Bot API (aiogram)
  ЦБ РУз (курсы) ──cron──►  │  (схема: см. приложение)    │ ──► TG-канал (публикации)
  Web App (заявки) ──────►  │                             │
                            └─────────────────────────────┘
         Пайплайн: raw_items → парсер (rules/LLM) → signals → alerts/price_points/reports
```

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2 + Alembic, Celery + Redis, Telethon (userbot), aiogram 3 (бот), PostgreSQL 16; фронтенд — Next.js (дашборд), React + @telegram-apps/sdk (Web App); LLM — Anthropic API (модель класса Haiku для извлечения, класса Sonnet для отчётов); Docker Compose, Nginx, VPS.

**Принципы (обязательные к реализации):**
- Сырые данные неизменяемы (raw_items); любой парсинг воспроизводим; дедупликация по content_hash.
- Каждый LLM-вызов журналируется (parse_runs: модель, версия промпта, токены).
- Сбой одного источника не влияет на остальные и на доставку отчётов (деградация блоками).
- Все фоновые задачи идемпотентны (повторный запуск не создаёт дублей).

## 4. Функциональные требования

### 4.1. Сбор данных

**FR-1. Парсер UZEX.**
Система собирает данные перечисленных в п. 2.1 разделов uzex.uz каждые 15 минут в торговые часы (пн–пт 9:00–18:00 Asia/Tashkent) и 1 раз/час вне их. Из позиций извлекаются: наименование товара, грейд (текст), объём, цена, валюта, секция, контрагенты (если опубликованы), дата/время. Позиции, относящиеся к полимерам (справочник products + синонимы), создают signals; остальные сохраняются в raw_items со статусом irrelevant. Нерас­познанный товар — алерт типа source_failure не создаёт, попадает в очередь ручной классификации.

**FR-2. Мониторинг Telegram.**
Userbot читает новые сообщения согласованных публичных каналов. Каждое сообщение → raw_items → LLM-классификация: релевантно/нет; при релевантности — извлечение структуры сигнала. Точность извлечения подтверждается на тестовой выборке (см. п. 6). Userbot работает с выделенного аккаунта заказчика; риск ограничений со стороны Telegram несёт заказчик (п. 7).

**FR-3. Международный контур (Фаза 2).**
(а) Ежедневный импорт ценовых значений SunSirs (PP, HDPE, LDPE, LLDPE, PVC, PET — Китай) и расчётных цен фьючерсов DCE (PP, LLDPE) в price_points. (б) Мониторинг до 15 публичных Telegram-каналов трейдеров РФ/КЗ/Турции в общем пайплайне; извлечение работает на RU/EN/TR; сигналы помечаются регионом источника. (в) ETS Kazakhstan — после верификации (допущение 8): еженедельный импорт ценовых индикаторов ЕАЭС по полимерным позициям. Недоступность любого внешнего источника → пропуск периода, алерт команде, отчёты публикуются без соответствующего блока.

**FR-4. Курсы валют.** Ежедневный импорт официального курса ЦБ РУз; пересчёт отображается в UI рядом с оригинальной валютой, оригинал всегда сохраняется.

### 4.2. Web App клиента

**FR-5. Авторизация** — через Telegram initData (проверка подписи на backend); первый вход создаёт clients.

**FR-6. Подача заявки** — мастер из 4 шагов по мокапам: (1) продукт/марка/тип, (2) объём + целевая цена, (3) условия поставки: Incoterms, страна, порт/город, желаемая дата, срок действия, (4) комментарий + файлы (PDF/Excel/JPG, до 10 МБ, до 5 шт). Подтверждение с номером REQ-ГГГГ-ММ-ДД-NNNNN.

**FR-7. Мои заявки** — список с текущими статусами и историей; push-уведомление через бота при смене статуса.

**FR-8. Новости** (Фаза 2) — лента опубликованных отчётов.

**FR-9. Языки** — RU/UZ, переключение в настройках, определение по language_code Telegram при первом входе.

### 4.3. Дашборд (внутренний)

**FR-10. Live Feed** — единая лента (v_live_feed) с фильтрами: период, продукт, тип сигнала, источник, срочность; обновление без перезагрузки (поллинг ≤30 сек или SSE).

**FR-11. Purchase Requests** — таблица заявок клиентов + карточка: детали, файлы, AI-блок (score, сравнение целевой цены со средней по price_points), действия: смена статуса, назначение ответственного, заметки. Все действия — в audit_log.

**FR-12. Price Trends** — график цен по продукту/рынку из price_points; Фаза 2: оверлей внешних индексов.

**FR-13. Sources** — состояние источников: последний успешный сбор, число подряд неудач, вкл/выкл.

**FR-14. Alerts** — лента алертов; конструктор правил (продукт, порог объёма/цены, срочность, каналы доставки).

**FR-15. Роли** — admin (всё + пользователи), analyst (данные + правила + подтверждение отчётов), trader (просмотр + работа с заявками), viewer (только просмотр).

### 4.4. Бот и публикации

**FR-16. Бот команде** — доставка алертов в DM/группу по правилам; rate limit Telegram соблюдается очередью (deliveries).

**FR-17. Бот клиентам** — приветствие, кнопка Web App, уведомления о статусах.

**FR-18. Отчёты (Фаза 2)** — генерация утреннего отчёта к 8:30 Asia/Tashkent: цены UZEX за вчера (изменения к предыдущему дню), число и структура заявок, заметные сигналы, внешний фон. Черновик появляется в дашборде; публикация в канал — только после нажатия «Подтвердить» пользователем с ролью analyst/admin. Автопубликации без подтверждения нет. Каждая публикация содержит атрибуцию: «По данным uzex.uz» (требование источника).

### 4.5. AI-обработка

**FR-19. Извлечение** — структурирование сообщений каналов и свободного текста заявок по фиксированной JSON-схеме; версия промпта и модель журналируются.

**FR-20. Скоринг** — lead_score (0–1) и классификация HOT/MEDIUM/LOW по правилам + LLM; формула/промпт согласуются с заказчиком; результат хранится в signals.ai/requests.ai и пересчитывается при смене версии промпта.

**FR-21. Бюджет LLM** — конфигурируемый дневной лимит токенов; при превышении извлечение деградирует в rule-based + очередь на дообработку, алерт админу.

**FR-22. Конструктор источников.** Пользователь с ролью admin добавляет источник через мастер в дашборде: выбор типа (Telegram-канал / веб-страница с AI-извлечением / HTML-таблица / RSS) → заполнение формы → тестовый прогон с превью извлечённых записей → включение. Включение источника без успешного теста невозможно. Для AI-источников отображается расход токенов. Данные новых источников проходят общий конвейер (сырой слой, дедупликация, сигналы, алерты) без доработок.

## 5. Нефункциональные требования

- **Производительность:** лента и таблицы дашборда — ответ API ≤500 мс при объёме до 1 млн signals; Web App — первая отрисовка ≤3 с на 3G.
- **Надёжность:** автоперезапуск воркеров; ежедневный бэкап PostgreSQL (pg_dump) с хранением 14 дней + еженедельный полный с хранением 8 недель; документированная процедура восстановления.
- **Безопасность:** HTTPS повсеместно; секреты в .env вне репозитория; проверка подписи initData; хэширование паролей (argon2); доступ к дашборду только по учёткам; audit_log на все изменения заявок и публикации.
- **Наблюдаемость:** структурированные логи; алерт при падении любого сборщика >3 циклов подряд; страница /health.
- **Локализация времени:** все timestamp в UTC в БД, отображение в Asia/Tashkent.

## 6. Критерии приёмки (выборочно, по фазам)

**Фаза 1:**
1. Заявка, поданная через Web App, появляется в дашборде ≤10 сек; смена статуса доставляет клиенту уведомление ≤30 сек.
2. Полимерные позиции тестового торгового дня UZEX присутствуют в signals с корректными полями (проверка по контрольной выборке ≥50 позиций, точность ≥95%).
3. На контрольной выборке из 100 сообщений каналов (готовит заказчик): полнота обнаружения релевантных сигналов ≥80%, точность извлечения полей у обнаруженных ≥85%. Ошибки LLM-извлечения сверх этих порогов не являются дефектом.
4. Отключение одного источника не прерывает работу остальных; алерт о сбое приходит ≤30 мин.
5. Восстановление БД из бэкапа на чистом сервере по документации — ≤2 часов.
6. Администратор без участия разработчика добавляет через дашборд новый публичный сайт и новый Telegram-канал; сигналы из них появляются в ленте; источник с неуспешным тестом включить невозможно.

**Фаза 2:**
6. Утренний черновик отчёта формируется к 8:30; в канал без подтверждения не уходит ничего.
7. При недоступности SunSirs отчёт публикуется без внешнего блока, без ошибок.
8. На контрольной выборке из 50 сообщений международных каналов (RU/TR, готовит заказчик): полнота обнаружения ≥75%, точность извлечения ≥80% (пороги ниже Фазы 1 из-за мультиязычности).

## 7. Ограничения и распределение рисков (включить в договор)

1. **Источники данных.** Система использует только: открытые страницы uzex.uz (с обязательной атрибуцией), согласованные публичные Telegram-каналы, бесплатные открытые индексы (SunSirs, DCE), официальные курсы ЦБ РУз, данные собственных клиентов. Подключение подписочных сервисов — только при наличии у заказчика действующей подписки и только во внутренний контур (без публикации); оформляется отдельным соглашением.
2. **Userbot.** Мониторинг каналов через пользовательский аккаунт допускается Telegram ограниченно; возможны ограничения аккаунта. Аккаунт(ы) предоставляет заказчик; разработчик реализует щадящий режим чтения, но не гарантирует отсутствие блокировок.
3. **Изменения источников.** Изменение вёрстки uzex.uz или структуры каналов ломает сборщики; восстановление — в рамках поддержки (п. 8), не гарантийный дефект.
4. **AI-качество.** Пороговые значения качества зафиксированы в п. 6; всё сверх — итеративное улучшение в рамках поддержки.
5. **Публикуемый контент.** Ответственность за содержание публикаций в канал несёт заказчик (подтверждающий публикацию).

## 8. Этапы, сроки, поддержка

| Этап | Содержание | Срок |
|---|---|---|
| 0. Подготовка | Доступы (VPS, бот-токены, аккаунт userbot, список каналов), уточнение справочника продуктов/грейдов | 1 нед |
| 1. Ядро данных | БД, парсер UZEX, raw-пайплайн, импорт курсов | 2 нед |
| 2. Клиентский контур | Web App + бот + заявки в дашборде (минимальный вид) | 2 нед |
| 3. Дашборд | Полные экраны Фазы 1, алерты, роли | 2 нед |
| 3a. Конструктор источников | Типы: веб-страница (AI), HTML-таблица, RSS; мастер с тестовым прогоном | 1 нед |
| 4. Мониторинг каналов | Userbot + LLM-извлечение + приёмка по выборке | 1.5 нед |
| Приёмка Фазы 1 | Критерии п. 6 (1–6) | 0.5 нед |
| 5. Фаза 2 | Отчёты + международный контур (индексы, RU/KZ/TR-каналы, верификация ETS) + связывание контрагентов | 5–6 нед |

Итого: Фаза 1 ≈ 10 недель, Фаза 2 ≈ +5–6 недель. Сроки действительны при предоставлении доступов в Этапе 0 и ответах заказчика ≤2 рабочих дней.

**Поддержка (обязательна, отдельный ежемесячный договор):** починка сборщиков при изменении источников, ротация userbot-аккаунтов, тюнинг промптов, добавление каналов, мониторинг. Без поддержки работоспособность сборщиков со временем деградирует по независящим от разработчика причинам.
