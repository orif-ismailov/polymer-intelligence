<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram servers → POST /telegram/webhook/{secret} | Only Telegram (knowing the secret) may post updates; forgeries must be rejected |
| Bot push → client | A push must only reveal the recipient client's own request (no cross-client leak via deep link) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-11 | Spoofing | forged webhook updates | mitigate | Secret in path AND X-Telegram-Bot-Api-Secret-Token header both compared to WEBHOOK_SECRET via hmac.compare_digest; mismatch → 403 (Task 2) |
| T-03-12 | Information disclosure | deep-link leaking another client's request | mitigate | The deep link targets the recipient's own request id; the Web App route /requests/{id} is IDOR-scoped by initData (03-02 T-03-07) so even a guessed id returns 404 for non-owners (Task 2 + 03-02) |
| T-03-13 | Denial of service | notify task crashing the worker | mitigate | Task wrapped in try/except, returns error dict, never raises (Task 2) |
| T-03-14 | Tampering | secret token in tracked source | accept→mitigate | WEBHOOK_SECRET loaded only from .env (config.py contract), never literal in source (REQ-nfr-security, pre-existing) |
</threat_model>
