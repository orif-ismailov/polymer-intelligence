# Онбординг-карта IMEX AI

Материал для визуальной карты продукта и ролей. Собран **вождением живого продукта в
браузере** (`localhost:5173` портал, `localhost:3000` дашборд) на обнулённой базе, а не по
документации и не по коду.

Итог: **114 кадров в десяти частях, семь сквозных лент, двенадцать статусных машин и
50 находок.**

## Что здесь

| Файл | Что это |
|---|---|
| `board-model.json` | Единое описание карты, из которого генерируются оба носителя |
| `build.mjs` | Генератор: JSON → `.excalidraw` + `.html` |
| `findings.md` | 50 находок с воспроизведением и доказательствами |
| `plan.md` | Задача, 18 указаний заказчика, правила работы, чек-лист |
| `annotate.js` | Аннотатор кадров: выноски привязаны к реальным прямоугольникам элементов |
| `dist/` | Собранные носители (вне git) |
| `../../.tmp-onboarding/shots/` | Кадры (вне git) |

Сборка:

```bash
node .planning/onboarding-board/build.mjs
```

## Носители результата

Оба генерируются из `board-model.json`, поэтому разойтись не могут:

1. **`.excalidraw`** — сцена для excalidraw.com (перетащить файл на холст). ~23 МБ: кадры
   встроены как уменьшенные JPEG прямо в сцену.
2. **Одностраничный HTML** — читаемая карта с навигацией; кадры лежат рядом в `dist/shots/`,
   папка переносится целиком.

**В git лежат только исходники.** `dist/` и кадры — нет: 87 МБ снимков живого стенда. Носители
пересобираются командой выше, пока кадры на месте.

FigJam-доска начата (https://www.figma.com/board/nvB8kXCluldAh6XU2ARVcK), но **заброшена**:
тариф Figma Starter даёт 20 вызовов MCP в месяц, лимит исчерпан после секции 0.

## Как читать

Карта идёт сверху вниз и рассчитана на чтение подряд:

| Раздел | Что отвечает |
|---|---|
| 0–2 · Легенда, карта продукта, ролевая модель | Что это за продукт и почему роль компании, а не пользователя, открывает фичи |
| 3.1–3.10 · Части A…J, 114 кадров | Что происходит на каждом экране; под кадром — что выяснилось |
| 13–19 · Сквозные ленты | Как действие одной роли запускает работу другой (swimlane) |
| 20 · Статусные машины | Путь сущности слева направо и выходы, из которых вперёд не идут |
| 21 · Находки | 50 находок, сгруппированных по виду: блокирует / дефект / правило / работает |
| Не исследовано | Честный список того, чего на карте нет, и почему |

Секция находок строится **из `findings.md`** самим генератором, поэтому список на доске и
разбор в файле не могут разъехаться.

## Визуальный язык

Цвет отвечает на «кто действует», форма — на «что это за шаг», бейдж — на «откуда мы знаем».

| Цвет | Значение |
|---|---|
| 🔵 синий | действие пользователя |
| 🟣 фиолетовый | система делает сама (Celery, бэкенд) |
| 🟡 жёлтый | бизнес-правило |
| 🟢 зелёный | успешный исход |
| 🔴 красный | ошибка, отказ, отклонение |
| ⚪ серый | состояние сущности, справка |
| 🟠 оранжевый | внешний рельс: Didox, E-IMZO, госреестр, банк |

| Бейдж | Значение |
|---|---|
| ✓ | проверено в браузере — есть запись сети или строка в Postgres |
| ⌘ | из кода — прочитано в исходниках, в браузере не выполнено |
| ? | требует уточнения — воспроизвести не удалось |

## Стенд, на котором всё снято

База обнулена `DROP SCHEMA` → `alembic upgrade head` → сидеры (`seed_reference`, `seed_staff`,
`seed_sources`, `seed_substances`, `seed_contract_templates`). Redis и бакет MinIO очищены.
Все данные создавались кликами по живому UI: пять компаний, офферы, тендер, образец, заявки
в логистику и лабораторию, договор с двумя подписями.

| Переключатель | Значение | Почему так |
|---|---|---|
| `gov_registry_mode` | `didox` | живой госреестр, реквизиты подтягиваются по ИНН |
| `didox_mode` | `live` | документный рельс включён (контур `testapi3.didox.uz`) |
| `verification_auto_approve` | сначала `false`, затем `true` | сняты обе ветки: ручное ревью и авто |
| `escrow_mode` | `stub` | переводы отмечает оператор вручную |
| `EIMZO_STUB` | `true` | **подпись принимается без проверки криптографии** (F-01) |

**Вход в кабинет изменился по ходу съёмки.** Был телефон + OTP `000000`; с коммита `12341af`
(миграция `0048`) — логин и пароль, которые выдаёт сотрудник на `/admin/portal-accounts`,
с обязательной сменой при первом входе. Кадры 3–5 описывают старую дверь и помечены как «было»,
кадры 107–110 — новую. Staff-вход не менялся: `admin@polymer.uz`.

**Справочник Didox знает один наш ИНН из трёх** — проверено тремя запросами подряд: `312616547`
(IMEX) находится, `590640341` (DIDOX) и `562353400` (TREADWAY) — нет. Отсюда закрыты рельс
договора через ЭДО (F-46) и эскроу (F-50).

Модуль E-IMZO видит пять корпоративных ключей: `562353400`, `514890380`, `575013376`,
`537302090` и `312616547` (наш). Пароль у всех `12345678`. На macOS ключи читаются из
`~/eimzo-test-keys/`; тому `DSKEYS` нужен `hdiutil attach`, если модуль их не видит.
