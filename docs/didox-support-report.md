## 1. Подписание публичной оферты не работает

Порядок из вашей документации (`integrators-newoffersign`) выполнен точно:

```
GET  /v1/newoffer/base64                        → 200, PDF в base64, 499 284 симв.
POST /v1/documents/offer/create {"document": "<этот base64>"}
                                                → 500  Failed to store offer
```

Дело **не в содержимом и не в размере** — ответ одинаковый:

| что отправили | размер | ответ |
|---|---|---|
| ваш PDF оферты целиком | 499 КБ | `500 Failed to store offer` |
| первые 10 КБ того же base64 | 10 КБ | `500 Failed to store offer` |
| минимальный валидный PDF | 78 Б | `500 Failed to store offer` |

Тот же отказ воспроизводится на вашей собственной странице регистрации
`test3.didox.uz/registration`.

## 2. У этого эндпоинта другой контракт заголовка

Он JWT-верифицирует **само значение** `Partner-Authorization`, поэтому обязательный для
остального API префикс `Bearer` его роняет:

```
Partner-Authorization: Bearer <token>  → 500 {"statusCode":500,"message":"invalid token","error":"JsonWebTokenError"}
Partner-Authorization: <token>         → авторизация проходит (422 «Поле document обязательно.»)
Authorization: Bearer <token>          → 401 {"message":"No Partner Authorization header passed"}
```

Просьба выровнять с остальным API либо явно описать исключение в документации.

документацией (§9 «Подписание исходящего документа»): `POST /{id}/sign` работает и валидирует
документ по существу, а `PUT /{id}/send` для типа `007` отвечает `422 Неподдерживаемый тип
документа`. Мы вернулись на `/sign`. Тот 500, судя по всему, был следствием неподписанной оферты —
если так, его стоит превратить в внятный 422, потому что 500 с именем PHP-переменной уводит
интеграторов в сторону на несколько дней.
