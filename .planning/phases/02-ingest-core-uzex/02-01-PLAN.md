<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker/beat → Redis broker | Celery serializes task args and results across the Redis broker; a compromised or exposed broker can inject task messages |
| config → process | Ingest tunables (timeout/retries/UA/delay) flow from .env into runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Spoofing/Tampering | Celery↔Redis broker message format | mitigate | Pin `task_serializer="json"`, `result_serializer="json"`, `accept_content=["json"]` in celery_app.conf — refuse pickle so a hostile broker message cannot execute arbitrary objects on deserialization |
| T-02-02 | Denial of Service | worker prefetch / lost task on crash | mitigate | `task_acks_late=True` + `worker_prefetch_multiplier=1` so a crashed worker re-queues rather than silently drops the in-flight fetch (REQ-nfr-reliability) |
| T-02-03 | Information Disclosure | Redis broker network exposure | accept | Dev/single-VPS: Redis bound to the compose network only, not published beyond localhost in prod (compose `restart: unless-stopped`); documented as single-VPS trust boundary. Re-evaluated in 02-07 reliability hardening |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new package installs in this plan (Celery/Redis already in pyproject). If any install is introduced, route through the package legitimacy checkpoint before merge |
</threat_model>
