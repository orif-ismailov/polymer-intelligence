# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## IMEX AI — Deal Lifecycle: Trade Room, комплаенс химии, лаборатории, платёжно-подписные провайдеры

Версия 1.0 · 27.07.2026 · Статус: на согласование
Трек: `deal-lifecycle` (продолжение `company-verification` R1–R3; контракты R3 — «seed of the Deal Lifecycle domain»)

---

## 1. Цель

Закрыть разрыв между текущей платформой и целевым видением IMEX AI (зафиксировано в
продуктовых обсуждениях 07.2026): довести платформу от «маркетплейс объявлений + контракты»
до **полного жизненного цикла сделки** между двумя верифицированными компаниями:

```
RFQ покупателя → оффер поставщика → Trade Room (чат + документы)
→ контракт (E-IMZO | Didox) → оплата через Escrow (банк)
→ отгрузка → подтверждение получения → выплата продавцу → завершено
```

Плюс три поддерживающих контура:

- **Комплаенс химии** — CAS/HS-коды на продуктах, реестр опасных веществ, требование
  лицензии при публикации оффера с опасным веществом.
- **Лаборатории** — заказ лабораторного анализа (ручная обработка через партнёрскую
  лабораторию), лабораторный паспорт на оффере, запрос образца у продавца.
- **Внешние провайдеры** — adapter-контуры для Didox (э-документооборот), Escrow-банка
  и гос-реестров (проверка компании/лицензий). Живые интеграции включаются позже,
  до получения credentials работают стабы + ручные операторские действия.

### 1.1. Что система ДЕЛАЕТ и НЕ ДЕЛАЕТ (зафиксировать с заказчиком)

Система **проводит** сделку по управляемому жизненному циклу, **фиксирует** каждый переход
статуса, **хранит** документы сделки неизменяемо и **уведомляет** стороны.

Система **не является** платёжной системой (деньги движутся только на стороне банка-эскроу),
**не даёт** юридического вердикта о праве компании торговать веществом (комплаенс-подсказка,
не заключение — см. ARCHITECTURE §0.2), **не выполняет** лабораторный анализ (ручной процесс
партнёрской лаборатории, платформа только оркеструет заявки и хранит результат).

## 3. Скоуп

### 3.1. Блок A — Trade Room + Deal Lifecycle (ядро)

| Компонент | Входит |
|---|---|
| Агрегат `Deal` | Комната сделки, создаётся при акцепте оффера/отклика на RFQ; стороны = две верифицированные компании; ссылки на request/offer/contract |
| Машина состояний сделки | `negotiation → contract_pending → contract_signed → payment_pending → paid_escrow → shipped → delivered → completed` + `cancelled`, `disputed` (таблица переходов — данные, по образцу `request_service.VALID_TRANSITIONS`) |
| Чат сделки | Обмен сообщениями покупатель↔продавец внутри Deal (только участники + staff read-only); текст + вложения через storage_service |
| Документы сделки | Единая вкладка: контракт, инвойс, лаб-паспорт, транспортные документы, произвольные вложения; append-only |
| Отклик на RFQ | Поставщик отвечает на опубликованный RFQ структурированным оффером (цена/объём/срок) → акцепт покупателем открывает Deal |
| Связь с контрактами R3 | «Создать договор» изнутри Deal; подписанный контракт двигает Deal в `contract_signed` через domain event (без прямых cross-context импортов) |
| Уведомления | Portal-notifications + Telegram стаффу на ключевые переходы |
| Стафф-надзор | Dashboard: список/карточка сделок, таймлайн статусов, чат read-only, ручное разрешение `disputed` |

### 3.2. Блок B — Комплаенс химии (CAS/HS + реестр опасных веществ)

| Компонент | Входит |
|---|---|
| Справочник веществ | `substances`: название (ru/uz/en), **ТН ВЭД/HS-код (первичный юридический идентификатор — официальные перечни РУз используют наименования + ТН ВЭД, не CAS)**, CAS-номер (вторичный, для AI/международных SDS), класс опасности, **уровень регулирования** (см. ниже), **режим регулирования** (`precursor_list_iv` ПКМ-330 / `explosive_toxic` ПКМ-782+397 / `strong_acting` ПКМ-818 / `pkm916_import`), **пороговая концентрация и годовой лимит изъятия** (Список IV регулирует, напр., ацетон только ≥60%, соляную к-ту ≥15%, с изъятием ≤12 кг/год), категория требуемой лицензии, **перечень обязательных документов** (SDS/TDS/COA/сертификат происхождения), синонимы; **сидируется оцифровкой официальных перечней ПКМ** (`seed_substances`, идемпотентный, версионируемый); редактируется в админке |
| 4 уровня регулирования | 🟢 `free` — свободная продажа; 🟡 `docs_required` — публикация требует загрузки документов (SDS/TDS/COA по списку вещества); 🟠 `license_required` — активная лицензия компании нужной категории/режима; 🔴 `prohibited` — размещение на платформе запрещено (перечни ПКМ-916; также рекомендация: вещества Списка IV без подтверждённой лицензии не показывать вовсе). **Полимеры PP/PE/PVC/PET/PS подтверждённо не входят ни в один перечень — `free`** (оговорка: отходы пластмасс ТН ВЭД 3915 — режим ПКМ-916) |
| Поля на продуктах/офферах | `cas_number`, `hs_code`, FK на substance у `SellerOffer` (и опционально у Request) |
| AI-определение | При публикации оффера LLM-экстрактор определяет вещество по тексту → кандидат CAS/HS + уровень регулирования → подтверждение продавцом (никогда не автозапись без подтверждения); экран прогрессии проверки («Определяем вещество → Проверяем перечень РУз → …») |
| Проверка при публикации | По уровню регулирования: `docs_required` → чек-лист обязательных документов на оффере; `license_required` → активная лицензия (`compliance`-контекст R1), нет — блокировка с объяснением + CTA загрузки; `prohibited` → публикация невозможна с указанием основания. Проверка компании при регистрации НЕ дублируется — комплаенс срабатывает именно в момент публикации товара (решение из продуктового обсуждения) |
| Интеграция с гос-реестром опасной химии | Adapter-интерфейс (см. блок D); до live-подключения источник истины — локальный справочник |
| Runtime-настройка | `dangerous_check_enforced` (default off) — включение блокировки публикации — операторское действие, не деплой |

### 3.3. Блок C — Лаборатории + образцы

| Компонент | Входит |
|---|---|
| Лаб-паспорт на оффере | Тип документа `lab_passport` у файлов оффера; бейдж «Лабораторный паспорт» / «Laboratory Verified» на карточке (отдельно помечается независимое лаб-подтверждение через платформу); **фильтр в маркете** «только с лаб-паспортом» |
| Заказ лаб-анализа | `LabOrder`: продавец (или покупатель по сделке) заказывает анализ → статусная машина `submitted → accepted → sample_awaited → in_analysis → done / rejected`; обработка **ручная** («мы свяжемся с вами, согласуем лабораторию, стоимость и порядок передачи образцов» — менеджер IMEX связывается сам); результат = загруженный паспорт, прикрепляется к офферу/сделке |
| Партнёрские лаборатории | Справочник лабораторий (админка); компания-лаборатория может иметь роль `laboratory` (enum уже существует) |
| Образцы на оффере | Блок в форме оффера: образцы доступны/нет, бесплатно/платно (стоимость), срок отправки |
| Запрос образца | `SampleRequest` покупателя по офферу: `requested → accepted / declined → sent → received / rejected_by_buyer`; при отправке продавец указывает количество, курьерскую службу, трек-номер; адрес доставки из профиля компании покупателя |
| Уведомления | Продавцу о запросе образца, покупателю о статусах, оператору о новых лаб-заявках |
| AI-совместимость (опция, R5+) | По лаб-параметрам (MFI, плотность и т.д.) AI отвечает покупателю, подходит ли материал под его технологию (литьё/экструзия/выдув/плёнка/трубы) — 🟢/🟡/🔴 с пояснением; за runtime-настройкой, отдельная prompt-семья |

### 3.4. Блок D — Внешние провайдеры (adapter + стаб)

Все — через integration-gateway паттерн R3 (`backend/app/integrations/`): typed-клиент,
таймауты, circuit breaker, `integration_call_log`, деградация без блокировки пайплайна.
**До получения credentials каждый провайдер работает в режиме `stub`** (runtime-настройка
`<provider>_mode: stub | live`), а соответствующие шаги выполняются вручную оператором.

Детальный фундамент по каждому провайдеру (факты из официальных источников, контракты
адаптеров, открытые вопросы) — в **`INTEGRATIONS.md`** (той же директории). Сводка:

| Провайдер | Контракт адаптера | Стаб-режим (до credentials) |
|---|---|---|
| **Didox** (ЭДО; публичная партнёрская API-документация api-docs.didox.uz ✅) | `auth_user` (user-key по ЭЦП), `create_contract` (тип «Договор НК» — юридически значимый, роуминг my.soliq.uz), `timestamp`, `sign`, `join_signatures`, `list_updated` (**polling — webhooks у Didox нет**), `fetch_archive` (доказательная копия → S3). Подпись создаётся нашим существующим E-IMZO-флоу — Didox только штампует и доставляет | Контракт подписывается существующим E-IMZO-контуром R3 (Didox = альтернативный signing-провайдер на уровне `contract_service`, выбор per-contract). Тест-контур testapi3.didox.uz доступен сразу после partner-token |
| **Escrow-банк** (API гарантирован статусом гос-проекта, сроки неизвестны) | `open_escrow(deal, amount)`, `get_status`, `request_release`, `request_refund` + webhook-inbox `provider_events` И fallback-polling (форма уведомлений банка неизвестна). Реквизиты счетов не храним — только `provider_ref` | Оператор вручную отмечает `funded/released/refunded` в дашборде (двойное подтверждение + аудит); статусная машина `EscrowPayment` одна и та же в обоих режимах. Для крупных сделок параллельный законный инструмент — аккредитив UZS |
| **Гос-реестры** (официальный API-канал — только ПЦД; процесс непрозрачен, решается админресурсом проекта) | `lookup_company(inn)`, `lookup_licenses(inn)`, `lookup_vat(inn)` → immutable snapshot + авто-чеки `VerificationCase` (`method: registry`) | Ручная стафф-верификация R1 + **E-IMZO R3 (сильнейший доступный механизм — уже работает)**; опционально полуавтомат: операторская сверка по открытым сервисам (НДС-реестр my.soliq.uz, лицензии по ИНН на ЕПИГУ) с сохранением evidence |
| **Реестр опасной химии** (машиночитаемого гос-реестра НЕ существует ✅) | `lookup_substance(hs_code\|name)` — интерфейс закладываем, реализация надолго stub | **Собственный справочник `substances` — источник истины по архитектуре, не времянка**: оцифровка официальных перечней (Список IV прекурсоров ПКМ-330, ПКМ-782/397, ПКМ-818, ПКМ-916) в идемпотентный сид |

Статусная машина `EscrowPayment`: `pending → funded → released / refunded`, привязана к Deal;
переходы двигают Deal (`payment_pending → paid_escrow`, `delivered → completed` после release).

### 3.6. Зафиксированные допущения (изменение = изменение скоупа)

1. **Внешние договорённости — на стороне заказчика:** банк-эскроу (API гарантирован
   статусом гос-проекта, сроки получения неизвестны), Didox (partner-token у
   аккаунт-менеджера; тест-контур доступен сразу), доступ к ПЦД для гос-реестров
   (админресурс проекта), партнёрская лаборатория. Платформа готовит adapter-контуры
   и стабы; live-режим каждого провайдера включается отдельно после получения доступа
   и интеграционного тестирования. Сроки live-подключений в настоящее ТЗ не входят.
2. **Степень известности API различна** (детали — `INTEGRATIONS.md`): Didox — публичная
   документация, адаптер можно писать целиком уже сейчас; банк и ПЦД — форматы неизвестны,
   контракты проектируются по нашей доменной модели, маппинг на реальный API — отдельная
   задача на провайдера (типовая оценка: 3–7 дней после получения документации и тестового
   контура, включая обработку ошибок/таймаутов/недоступности и синхронизацию статусов);
   гос-реестра химии не существует — свой справочник (не времянка).
3. **Деньги не проходят через платформу.** Escrow — счёт и операции банка; платформа
   хранит только статусы и ссылки на банковские идентификаторы операций.
4. **Лабораторный анализ — ручной процесс.** SLA лаборатории вне контроля платформы;
   статусы двигает оператор. Кэшбэк-расчёты с лабораторией — вне скоупа (учёт можно
   вести по `LabOrder`-журналу).
5. **Комплаенс-проверка опасной химии — подсказка, не юридический вердикт**
   (ARCHITECTURE §0.2). Ответственность за законность сделки несут стороны.
6. **Справочник опасных веществ** (первичный список CAS + категории лицензий)
   предоставляет заказчик; без него блок B стартует с пустым справочником и
   выключенной блокировкой.
7. **Чат сделки** — не мессенджер: без typing-индикаторов, реакций, редактирования;
   доставка — polling/SSE по образцу live feed; push — существующие каналы уведомлений.
8. **Споры (`disputed`)** разрешает оператор вручную (перевод сделки в
   `cancelled`/возврат в предыдущий статус + комментарий). Арбитражный регламент —
   организационный документ заказчика, вне ТЗ.
9. Дизайн portal-экранов — в существующей дизайн-системе портала; отдельные мокапы
   не рисуются, приёмка по функциональности.

### 3.7. Вне скоупа (явно)

- Нативные iOS/Android приложения (клиентская поверхность — portal + Telegram Mini App).
- Подписки/тарифы/billing платформы.
- Отзывы и рейтинги компаний (кандидат на следующий трек — данные для них появятся
  из завершённых сделок).
- Логистический модуль (трекинг перевозок, интеграции с перевозчиками, таможенный
  статус груза) — в сделке только текстовый трекинг + документы.
- **Trade Finance сверх escrow**: аккредитивы (L/C), банковские гарантии, факторинг,
  страхование сделок, финансирование поставок — обсуждались в видении, отдельный трек
  после запуска escrow.
- Проверка санкционных списков, судебных дел и исполнительных производств в
  верификации; AI Trust Score компаний.
- Видеозвонки / CRM-функции сверх чата сделки.
- ERP-интеграции (1С, SAP и т.п.), публичный API платформы для третьих сторон.
- Автоматическая выплата/возврат средств — только по подтверждению банка.
- Didox как канал *первичной* верификации компании.

## 4. Функциональные требования

### 4.1. Deal Lifecycle (блок A)

- **FR-D1.** Отклик поставщика на опубликованный RFQ: структурированная форма
  (цена, объём, инкотермс, срок поставки, комментарий); покупатель видит список
  откликов на свой RFQ; акцепт одного отклика создаёт Deal (остальные отклики
  получают статус `not_selected`, уведомление).
- **FR-D2.** Deal также создаётся из принятого inquiry по офферу (существующий
  `OfferRequest` → кнопка «Открыть сделку» у продавца).
- **FR-D3.** Обе стороны Deal — компании со статусом `verified`; иначе создание
  отклоняется типизированной ошибкой.
- **FR-D4.** Переходы статусов Deal — только по таблице переходов; каждый переход
  пишет audit + domain event + строку истории; недопустимый переход → доменная ошибка.
- **FR-D5.** Чат: участники — члены обеих компаний (roles owner/manager), staff —
  read-only; сообщения append-only; вложения ≤ 10 МБ через storage_service;
  обновление ленты чата ≤ 30 с (polling/SSE).
- **FR-D6.** Документы сделки: загрузка обеими сторонами, тип документа из
  фиксированного списка (contract, invoice, lab_passport, transport, other);
  удаление запрещено (только пометка «отозван» с аудитом).
- **FR-D7.** Контракт из сделки: предзаполнение переменных из Deal (продукт, объём,
  цена, инкотермс, стороны); событие `CONTRACT_ACTIVATED` переводит Deal в
  `contract_signed`.
- **FR-D8.** Отмена: до `paid_escrow` — любой стороной с причиной; после — только
  через `disputed` (оператор).
- **FR-D9.** Дашборд: `/deals` — список с фильтрами (статус, компания, период),
  карточка с таймлайном, чатом (read-only), документами, escrow-статусом; действия
  оператора: разрешение спора, ручные escrow-отметки (stub-режим).
- **FR-D10.** Расширения RFQ-формы (по мокапам new-design): чек-лист **требуемых
  документов от поставщика** (SDS, COA, сертификат происхождения, коммерческое
  предложение, другое) — отображается поставщику в карточке RFQ и в форме отклика;
  **видимость заявки**: только верифицированные поставщики (default) / все / выбранные
  компании; поле «требуемые характеристики» (свободный текст ≤300). Канал получения
  предложений — внутри платформы (email/Telegram-каналы поставок предложений — вне
  скоупа R4).

### 4.2. Комплаенс химии (блок B)

- **FR-C1.** CRUD справочника веществ в админке (admin only); поля: названия ru/uz/en,
  ТН ВЭД/HS-код (первичный юр-идентификатор), CAS (уникален, вторичный), класс опасности,
  уровень регулирования (`free | docs_required | license_required | prohibited`),
  режим регулирования (какой ПКМ), пороговая концентрация/годовой лимит изъятия,
  категория требуемой лицензии, перечень обязательных документов, синонимы, ссылка на
  акт-основание. Первичное наполнение — сид `seed_substances` из официальных перечней
  (Список IV ПКМ-330 с порогами, ПКМ-818, ПКМ-782, ПКМ-916); правка перечней = новая
  ревизия сида.
- **FR-C2.** Форма оффера: поле «вещество» с поиском по справочнику (название/синоним/CAS);
  выбранное вещество автозаполняет CAS/HS; ручной ввод CAS/HS допустим для веществ
  вне справочника.
- **FR-C3.** AI-подсказка: по тексту оффера (product_text/description) экстрактор
  предлагает вещество-кандидата с уровнем регулирования; продавец подтверждает или
  отклоняет; подсказка журналируется (prompt-версия по конвенции `parsing/prompts/`).
- **FR-C4.** При `dangerous_check_enforced=on`, по уровню регулирования вещества:
  `docs_required` → публикация требует загрузки документов из перечня вещества
  (SDS/TDS/COA…); `license_required` → активная `CompanyLicense` нужной категории,
  отсутствие → блокировка с CTA «загрузить лицензию» (существующий compliance-поток R1);
  `prohibited` → публикация невозможна, типизированная ошибка с основанием.
- **FR-C5.** Модерация видит комплаенс-статус оффера (вещество, уровень регулирования,
  документы, лицензия) в карточке модерации.
- **FR-C6.** Повторная проверка: комплаенс-статус пересчитывается при каждом
  редактировании/переопубликации оффера (лицензия могла истечь/аннулироваться
  между публикациями).

### 4.3. Лаборатории и образцы (блок C)

- **FR-L1.** Продавец загружает лаб-паспорт (PDF) на оффер; на карточке оффера —
  бейдж + просмотр документа; паспорт, полученный через платформенный `LabOrder`,
  помечается как независимое подтверждение («Laboratory Verified»).
- **FR-L2.** Заказ анализа: продавец с оффера (или сторона сделки из Trade Room)
  создаёт `LabOrder` (вещество, объём пробы, комментарий); оператор в дашборде ведёт
  статусы; финальный статус `done` требует загрузку паспорта, который прикрепляется
  к офферу/сделке.
- **FR-L3.** Запрос образца: покупатель по офферу создаёт `SampleRequest` (только если
  оффер помечен «образцы доступны»); продавец принимает/отклоняет; при отправке
  указывает количество, курьера, трек-номер; покупатель подтверждает получение или
  отклоняет образец; адрес — из профиля компании покупателя.
- **FR-L4.** Все статусные изменения — уведомления затронутой стороне
  (portal-notifications + существующие Telegram-каналы стаффу).
- **FR-L5.** Фильтр маркета «только с лабораторным паспортом» (и отдельно —
  «независимо подтверждённые»).

### 4.4. Провайдеры (блок D)

- **FR-P1.** `EscrowPayment` создаётся при переходе Deal в `payment_pending`
  (сумма = из контракта/сделки); в stub-режиме оператор отмечает `funded`/`released`/
  `refunded` в дашборде (двойное подтверждение: чекбокс + причина, audit); в live —
  статусы приходят от банка (webhook + опрос).
- **FR-P2.** Deal переходит `payment_pending → paid_escrow` только по `funded`;
  `delivered → completed` только по `released`. Прямой переход запрещён на уровне
  таблицы переходов.
- **FR-P3.** Didox-адаптер: интерфейс + стаб; выбор signing-провайдера контракта
  (`eimzo | didox`) — поле контракта; в stub-режиме доступен только `eimzo`.
- **FR-P4.** Гос-реестр-адаптеры: интерфейсы `lookup_company/lookup_licenses` + стабы;
  в live-режиме результат сохраняется snapshot-ом (immutable evidence) и апсертит
  авто-чеки открытого `VerificationCase` (`method: registry`); недоступность провайдера
  → чек `unavailable`, ручной путь не блокируется (инвариант R1).
- **FR-P5.** Все адаптеры: таймауты, circuit breaker, `integration_call_log`,
  типизированная `ProviderUnavailable`; вызовы — на выделенной Celery-очереди
  (существующая `verify` либо новая `integrations` — решение в плане).

### 4.5. AI supplier matching push (блок E)

- **FR-A1.** По публикации RFQ (при `rfq_supplier_push_enabled=on`): подбор компаний
  с офферами того же продукта/полимера; скоринг (совпадение продукта, верификация,
  наличие лаб-паспорта, свежесть оффера) с приоритетом по бизнес-роли
  (производитель → дистрибьютор → поставщик/импортёр → трейдер); top-N (настройка,
  default 10) получают portal-notification со ссылкой на RFQ и CTA «Откликнуться» (FR-D1).
- **FR-A2.** Рассылка журналируется; повторная публикация того же RFQ не дублирует
  уведомления.

### 4.6. Медиа (блок F)

- **FR-M1.** Загрузка/замена/удаление логотипа компании (owner/manager); JPEG/PNG ≤ 5 МБ;
  magic-byte MIME-проверка; замена перезаписывает ссылку, старый объект удаляется из S3.
- **FR-M2.** Загрузка фото в форме оффера (создание и редактирование до/после модерации —
  добавление фото к опубликованному офферу возвращает его на модерацию при включённой
  модерации); ≤ 8 фото на оффер, JPEG/PNG ≤ 10 МБ; первое фото — обложка.
- **FR-M3.** Отображение: обложка в списке маркета, галерея на странице оффера,
  логотип в профиле/шапке/каталоге компаний; отсутствие фото — нейтральный плейсхолдер
  (без ломки вёрстки).
- **FR-M4.** Выдача файлов только авторизованным поверхностям (portal-сессия / staff JWT);
  прямых публичных постоянных URL нет.

- Все существующие инварианты 00-IMPLEMENTATION-CONTEXT и ARCHITECTURE действуют:

- Тестирование: строгий TDD per task; полный `pytest tests/` перед каждым коммитом;
  e2e Playwright на демо-сценарии каждого этапа; mypy strict для новых сервисов.

## 7. Критерии приёмки (демо-сценарии = Definition of Done этапов)

1. **Deal happy-path (A):** покупатель публикует RFQ → поставщик получает push (E),
   откликается → покупатель акцептует → Trade Room: чат, документы → «Создать договор»
   → обе стороны подписывают E-IMZO (R3) → Deal `contract_signed` → оператор (stub)
   отмечает `funded` → продавец `shipped` → покупатель `delivered` → оператор `released`
   → Deal `completed`; полный таймлайн в дашборде; все переходы в audit.
2. **Комплаенс (B):** оффер с веществом из реестра (`license_required`) при включённой
   настройке не публикуется без активной лицензии; после загрузки и одобрения лицензии —
   публикуется; AI-подсказка вещества журналируется и требует подтверждения.
3. **Лаборатория (C):** заказ анализа с оффера → оператор ведёт статусы → загрузка
   паспорта → бейдж на оффере; запрос образца проходит `requested→accepted→sent→received`
   с уведомлениями.
4. **Стабы (D):** переключение `escrow_mode`/`didox_mode`/`registry_mode` — runtime,
   без деплоя; в stub-режиме все ручные действия оператора аудируются; отказ live-провайдера
   (симуляция) не блокирует остальной пайплайн (чек `unavailable`, circuit breaker).
5. **Медиа (F):** компания загружает логотип → виден в профиле/шапке/каталоге; продавец
   публикует оффер с 3 фото → обложка в списке маркета, галерея на странице оффера,
   фото в карточке модерации; невалидный файл (не JPEG/PNG, oversize) отклоняется с
   понятной ошибкой.
6. Регресс: весь существующий suite (backend + portal + dashboard e2e) зелёный.
