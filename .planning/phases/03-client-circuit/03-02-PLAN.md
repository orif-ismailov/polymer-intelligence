<objective>
Implement request_service (REQ-YYYY-MM-DD-NNNNN number generation, the dev-spec §3 status
machine, status history, notify enqueue) and the `/webapp/*` request + profile API surface:
POST/GET /webapp/requests, GET /webapp/requests/{id}, POST /webapp/requests/{id}/files,

and scopes data to the authenticated client (IDOR-safe).

requests with status history. Closes REQ-request-wizard (server side), REQ-my-requests,
REQ-webapp-i18n (language profile), and the request-side of REQ-webapp-auth.
Output: request_service.py, the four webapp router modules, main.py wiring, two test suites.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram client → /webapp/* | Every handler authenticates initData and scopes data to the verified client |
| Web App → POST /webapp/requests/{id}/files | Untrusted file + the request_id path param; ownership and file validity must be checked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-07 | Information disclosure (IDOR) | GET /webapp/requests/{id}, list, files | mitigate | Every query scoped to `client.id` from verified initData; cross-client id returns 404 (Task 2) |
| T-03-08 | Spoofing | client_id from request body | mitigate | client identity comes only from get_current_client; body never supplies client_id (Task 1 create_request signature takes client param, not body) |
| T-03-09 | Tampering | invalid status transition via API | mitigate | transition_status validates against VALID_TRANSITIONS server-side; ValueError→422 (Task 1) — client-facing API never sets status directly |
| T-03-10 | Repudiation | staff status changes untraced | mitigate | transition_status writes audit_log via write_audit when changed_by is staff (Task 1) |
| T-03-05 | Denial of service | oversized/too-many file uploads | mitigate | files router enforces MAX_FILES=5 + validate_upload 10 MB cap → 422 before MinIO write (Task 2, reuses 03-01) |
| T-03-04 | Tampering | wrong-type file upload | mitigate | magic-byte validate_upload → 422 invalid_file_type (Task 2, reuses 03-01) |
</threat_model>
