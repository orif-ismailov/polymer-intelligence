# E-IMZO

E-IMZO is Uzbekistan's national digital-signature stack. Two halves, and they are
almost always confused:

| Half | What it is | Where |
|---|---|---|
| **The desktop module** | A local app exposing crypto over a WebSocket ("CAPIWS"). It **signs**. The browser reaches it at `127.0.0.1`; it is never on a server. | user's machine |
| **`e-imzo-server`** | A UNICON-licensed Java sidecar that **verifies** a PKCS#7 against the national O'zDSt trust chain. Stock crypto libs cannot do this. | `deploy/`, profile `eimzo` |

The product never signs anything server-side. The browser signs, the backend verifies.

**Paths below are relative to the repo root.** The driver is
`.claude/skills/eimzo/capiws.mjs` — zero dependencies, needs Node ≥ 22 (global
`WebSocket`). Verified on Node v24.11.1 / macOS against **E-IMZO v6.4.7 Standard**.

Commands, all of them run:

```bash
node .claude/skills/eimzo/capiws.mjs version                    # module version + edition
node .claude/skills/eimzo/capiws.mjs apidoc                     # the module's OWN catalog: 11 plugins, 43 fns
node .claude/skills/eimzo/capiws.mjs apidoc --plugin pkcs7      # one plugin, with argument docs
node .claude/skills/eimzo/capiws.mjs certs                      # visible certificates + the id sign() needs
node .claude/skills/eimzo/capiws.mjs call pfx.list_disks        # raw escape hatch for any of the 43
node .claude/skills/eimzo/capiws.mjs version --tls              # force wss://127.0.0.1:64443
```

`apidoc` is the authoritative reference and it is **generated by the module you are
talking to** — prefer it over any web copy, which will be a different version. It is
the same data `https://127.0.0.1:64443/apidoc.html` renders; that page is an empty
shell that fetches this over the socket, which is why curling it gives you nothing.

### Sign something

```bash
node .claude/skills/eimzo/capiws.mjs sign --challenge "some-nonce" --cert 1
```

Prints base64 PKCS#7 to stdout. `--cert` is a 1-based index into `certs`, or a
literal `{"disk":…,"path":…,"name":…,"alias":…}` handle. Add `--detached` to omit
the signed content from the envelope (this repo does **not** — it signs embedded).

**This opens a native password dialog on the desktop and blocks until a human
answers it.** There is no headless path: the store password never crosses the
socket. That is the design, not a limitation to work around.

### Get a real test key

`test.e-imzo.uz` issues throwaway keys. **Use the PFX registrator, not the CKC one.**

```bash
# type=1 → legal entity (carries the org INN, which is what company verification matches on)
# type=0 → individual
curl -sk -X POST https://test.e-imzo.uz/registrator/public/pfx -d 'type=1' -OJ
#   → DS<PINFL>-test.pfx, ~4 KB, store password 12345678, valid 30 days
```

Each POST mints a fresh random identity. It is **rate limited to roughly one key per
2–3 minutes**, and the refusal is `HTTP 200` with
`{"status":-2,"message":"Too many requests. Please try again later."}` — so branch on
`content-type` (`octet-stream` = key, `application/json` = refusal), never on the
status code. Writing the body blindly gives you a 68-byte "`.pfx`" that fails much
later and looks like a corrupt key:

```bash
for i in 1 2 3; do
  until curl -sk -X POST https://test.e-imzo.uz/registrator/public/pfx -d 'type=1' \
          -D /tmp/h.txt -o /tmp/k.bin &&
        grep -qi 'octet-stream' /tmp/h.txt; do sleep 45; done
  fn=$(sed -nE 's/.*filename="([^"]+)".*/\1/p' /tmp/h.txt | tr -d '\r')
  cp /tmp/k.bin "/Volumes/DSKEYS/$fn"; echo "got $fn"
done
```

macOS only scans mounted volumes, so mount one **named `DSKEYS`** (see Gotchas):

```bash
hdiutil create -size 16m -fs "HFS+" -volname DSKEYS -ov /tmp/dskeys.dmg
hdiutil attach /tmp/dskeys.dmg
cp DS*-test.pfx /Volumes/DSKEYS/
node .claude/skills/eimzo/capiws.mjs certs        # picked up immediately, no restart
```

```
[1] ooo treadway inc — min gunner oletta
    store=pfx TIN=562353400 PINFL=37357422485008 serial=2187131f2
    valid 2026.08.18 14:55:14 → 2026.09.17 14:55:14
```

Then sign for real — `12345678` goes in the native dialog:

```bash
node .claude/skills/eimzo/capiws.mjs sign --challenge "polymer-test-challenge-001" --cert 1
```

The result is genuine national crypto — digest OID `1.2.860.3.15.2.3.2.1.1`, the
challenge embedded verbatim, chaining `MIN GUNNER OLETTA → TestCA → TestRoot`:

```bash
base64 -d < sig.b64 > sig.der
openssl pkcs7 -inform DER -in sig.der -print_certs -noout
# subject=CN=MIN GUNNER OLETTA, 1.2.860.3.16.1.2=37357422485008, UID=710975453,
#         1.2.860.3.16.1.1=562353400, O=OOO TREADWAY INC, title=Direktor
# issuer=CN=TestCA, O=test.e-imzo.uz
```

**These certs chain to `TestRoot`/`TestCA`, not the production UZ root** — the page
says so itself ("работает только с демо-сайтом и с тест-впн"). A sidecar loaded with
the production truststore (`deploy/eimzo/truststore`) will reject them. They are for
exercising the *signing* half; add the test root to a dev sidecar's truststore if you
need the verify half too.

The two national OIDs, which is what you actually read off a certificate:

| OID | Meaning | Maps to |
|---|---|---|
| `1.2.860.3.16.1.1` | organisation INN / STIR | `signer.org_inn`, matched against `company.tax_id` |
| `1.2.860.3.16.1.2` | PINFL (personal id) | `signer.pinfl`, only ever surfaced masked |

### Sign without a certificate

`stub-sign` emits the `EIMZO_STUB` envelope — base64 JSON, no crypto. This is how
the whole flow is exercised in dev/CI, and it is the only way to drive the backend
on a machine with no key:

```bash
node .claude/skills/eimzo/capiws.mjs stub-sign --challenge "$CH" --tin 305123456
node .claude/skills/eimzo/capiws.mjs stub-sign --challenge "$CH" --revoked   # force cert_revoked
```

The field names are the **stub's**, not the sidecar's — `tin` here becomes
`signer.org_inn`. Decoded by `app/integrations/eimzo/client.py::_stub_verify`.

## The CAPIWS protocol

From the shipped `e-imzo.js`, verified live:

- **Two transports, both live, identical:** `ws://127.0.0.1:64646/service/cryptapi`
  (plaintext) and `wss://127.0.0.1:64443/service/cryptapi` (TLS). The driver
  defaults to plaintext. `e-imzo.js` picks by *page* protocol — an https page must
  use `wss`, which is why browsers hit the self-signed-cert problem and a CLI need not.
- **One request per socket.** open → send one JSON → read one JSON → close. No
  multiplexing, no request id. Reusing a socket hangs forever.
- Request `{plugin, name, arguments:[…]}`, or a bare `{name:'version'|'apidoc'|'apikey'}`.
  **Every argument is a string** — numbers and booleans must be stringified (`'yes'`/`'no'`,
  not `true`/`false`).
- Response `{success, status, …payload}`; on failure `{success:false, reason}`.
- `apikey` registers the calling **Origin** against a shipped domain→key table and is
  **required** — without it every plugin call returns
  `{"success":false,"status":-1022,"reason":"API-key для домена null недействителен."}`.
  It looks optional only because the registration is **process-wide and sticky**: once
  any client has handshaken (a browser tab on an E-IMZO page, an earlier CLI run),
  everyone else rides free until the module restarts. The driver and
  `portal/src/shared/lib/eimzo/apikey.ts` each handshake once. Detect the refusal by
  **status `-1022`**, not by the message — the module can be switched to another
  language at runtime (`app.change_ui_lang`), so the Russian text is not stable.
  The module's full table, including domains not in `apidoc.html`, is readable on
  macOS with `defaults read uz.yt.eimzo`.
- **A production domain needs its own issued key.** The shipped table covers only
  `localhost`, `127.0.0.1`, `null`, `e-imzo.uz`, `*.soliq.uz` and `test.e-imzo.uz`.
  **`cabinet.ai-imex.com` is not registered**, and the key is verified against the
  domain so it cannot be self-generated — E-IMZO has to issue it. Until then, signing
  from the real cabinet cannot work; append the pair to `EIMZO_API_KEYS` when it
  arrives. This is an ops launch-blocker, not a code one.

### The 11 plugins

`app` (settings/UI) · `pfx` + `ytks` (file key stores) · `pkcs7` (**signing**) ·
`pkcs10` (keygen + CSR) · `pki` (enrollment) · `x509` (cert inspection) ·
`idcard` / `baikey` / `uzgrd` (hardware tokens) · `ckc` (crypto-container discovery).

The signing path is four calls and only three matter:

```
pfx.list_all_certificates()                    → [{disk,path,name,alias,TIN,CN,O,…}]
pfx.load_key(disk, path, name, alias)          → {keyId}      ← NATIVE PASSWORD DIALOG
pkcs7.create_pkcs7(data_64, keyId, 'no')       → {pkcs7_64}
pfx.unload_key(keyId)
```

`data_64` is base64 of the **raw bytes to sign**, and the module decodes it before
signing — so it signs the challenge text, not its base64.

## This repo's rails

**Browser** — `portal/src/shared/lib/eimzo/`. The feature depends on the 3-method
`EimzoBridge` (`probe`/`listCertificates`/`sign`), never on raw CAPIWS.
`CapiwsBridge` is the real one; `index.ts` prefers an injected
`window.__EIMZO_BRIDGE__`, which is how `portal/e2e/r3-eimzo.spec.ts`,
`r3-contracts.spec.ts` and `product-detail.spec.ts` run the whole flow with no
device. **Add a stub there, not a mock of the WebSocket.**

**API** — `app/domains/contracts/api_portal_eimzo.py`, two routes:

| Route | Meaning |
|---|---|
| `POST /api/v1/portal/companies/{id}/eimzo/challenge` | mint a single-use nonce in Redis, TTL `EIMZO_CHALLENGE_TTL_SECONDS` (300) |
| `POST /api/v1/portal/companies/{id}/eimzo/verify` | body `{"pkcs7": "<base64>"}` |

**Service** — `app/domains/contracts/eimzo.py`. On a good signature it does a lot in
one transaction: pops the challenge, verifies, stores immutable evidence to S3 +
encrypted person data, fills and **locks** the company requisites
(`identity_locked=True`), auto-confirms the signer as `owner`, marks
`eimzo_signature` passed, runs the other automated checks, and re-evaluates the case.

**Gateway** — `app/integrations/eimzo/client.py` → the sidecar's
`POST /api/verify-pkcs7` (5 s connect / 15 s read, circuit breaker at 5 failures/60 s).

### Exact responses, all reproduced live

| Case | HTTP | Body |
|---|---|---|
| valid | 200 | `{"ok":true,"holder_masked":"****0123","case":{…}}` |
| replayed / expired challenge | **400** | `{"detail":"challenge_expired"}` |
| cert INN ≠ company tax_id | **422** | `{"detail":{"error":"cert_company_mismatch","cert_inn":"99****99","company_inn":"30****11"}}` |
| revoked certificate | **200** | `{"ok":false,"reason":"cert_revoked",…}` |
| sidecar down / breaker open | **503** | `{"detail":"eimzo_unavailable"}` |

Note rows 3–5. A **revoked cert is a 200** — it is a domain verdict recorded on the
case, not an error. A **sidecar outage is a 503 and never blocks the manual
verification path**; that degradation is an architecture invariant, so if you find
yourself making an outage fail the case, you are breaking it. The mismatch 422
masks *both* INNs.

## Gotchas

- **`apidoc.html` is an empty shell.** Curling `https://127.0.0.1:64443/apidoc.html`
  gives you 8 KB of JavaScript and zero API documentation — the page calls `apikey`
  then `apidoc` over the socket and builds the DOM from the answer. Use
  `capiws.mjs apidoc`.
- **`pkcs10.generate_keypair` never returns headlessly.** It hangs indefinitely with
  no visible dialog and no error. `save_temporary_pfx` is the same family. Don't try
  to mint a test key from the CLI — the driver deliberately exposes neither. Use
  `stub-sign` instead.
- **The verify endpoint writes to S3 before it finishes**, so **no MinIO ⇒ HTTP 500**,
  even with `EIMZO_STUB=true`. The stub bypasses the *sidecar*, not the evidence
  store. This looks exactly like a signature bug and is not one.
- **`VERIFICATION_ENC_KEY` must be a valid Fernet key** (32 url-safe base64 bytes,
  44 chars, trailing `=`), not merely a long string. A wrong one fails at
  `_store_person_data`, i.e. *after* the signature verified and the S3 write
  succeeded — so the 500 points at the wrong half of the flow.
- **`RUN_MIGRATIONS_ON_STARTUP=true` silently kills logging.** The startup migration
  runs alembic's `fileConfig`, which reinstalls the root handlers — after that
  nothing is logged, including uvicorn's 500 tracebacks. You get a bare
  `Internal Server Error` and an empty log. Migrate up front and start the app with
  it `false`. (Same root cause as the `caplog` blindness in the real-DB tests.)
- **`pfx.load_key` blocks on a native dialog.** The driver gives it a 180 s timeout;
  a timeout there almost always means an unanswered prompt behind another window.
- **A certificate id is not an id.** `load_key` needs all four of
  disk/path/name/alias, so the bridge encodes them as a JSON string. Don't try to
  key certificates by serial.
- **On macOS, `~/DSKEYS` is ignored — it must be `/Volumes/DSKEYS/`.** Decompiling
  `E-IMZO.jar` settles it: `uz.eimzo.app.conf.PFXSearchConfig` holds
  `DSKEY_DIR_NAME="DSKEYS"` and `defaultMacosVolumesDirectory="/Volumes"`, and
  `CommonUtils$SubDirFilter` accepts only directories named `DSKEYS`. The home folder
  is never scanned, so a key dropped in `~/DSKEYS` is invisible with no error at all.
  `/Volumes` is root-owned, so the way in is to **mount a volume named `DSKEYS`**
  (`hdiutil ... -volname DSKEYS`). Pickup is immediate — no module restart.
- **`list_disks` is not the certificate list.** It returns `/Volumes/` even when the
  module can see nothing, and gains `/Volumes/DSKEYS/` once a key is visible. Trust
  `certs`. Any `disk` value other than one it returned fails with `Диск не найден`.
- **`list_all_certificates` returns duplicates on macOS.** Because the key volume *is*
  `/Volumes/DSKEYS`, it is simultaneously a mount point (its own disk, `path=""`) and a
  `DSKEYS` subdirectory of `/Volumes` (`disk="/Volumes/"`, `path="DSKEYS"`). Per-disk
  `list_certificates` is correct for each root, but `list_all_certificates` merges them
  and its dedup leaks — with 4 files on disk it returned **5** entries, one cert twice
  under two different `(disk, path)` pairs. Both handles load the same key, so this is
  cosmetic, but a picker built straight off the response shows the user the same
  certificate twice. Both the driver and `mapCapiwsCertificates()` dedup on
  `name + alias` — `disk`/`path` only record which door you walked through.
- **v6.4.7 returns no discrete cert fields.** `list_all_certificates` gives you only
  `{disk, path, name, alias}` — no `TIN`, `CN`, `O`, `serialNumber` or `validTo`. The
  whole subject DN plus validity is crammed into `alias`, **lowercased**:
  `cn=…,1.2.860.3.16.1.2=…,uid=…,1.2.860.3.16.1.1=…,o=…,t=…,serialnumber=…,validfrom=…,validto=…`.
  The driver's `parseAlias()` and the portal's `parseCertificateAlias()` unpack it.
  **This once broke registration outright**: the portal mapper read `c.TIN`, so
  `cert.tin` was always `undefined`, and `companyRegistrationSigner.getChallenge`
  throws `CertificateHasNoTin()` on a falsy tin — no one on v6.4.7 could register a
  company by certificate at all. Fixed by parsing the alias; if you touch that mapper,
  keep `e2e/eimzo-bridge.spec.ts` green.
- **The CKC registrator needs hardware and hangs without it.**
  `test.e-imzo.uz/registrator/public/ckc.html` ends in
  `pkcs10.create_pkcs10("ckc", …)` then `personalize` on `idcard`/`baikey`/`uzgrd` —
  all physical tokens. With none attached, `create_pkcs10` **never answers**: no
  error, no timeout, the page sits on «Ждите ...» forever. Use `pfx.html` instead.
- **These pages report every failure through `alert()`**, which Playwright silently
  dismisses. Override `window.alert` to capture them before driving one, or you will
  debug a blank page.
- **`detached` is `'yes'`/`'no'` strings**, and this repo signs with `'no'` (content
  embedded) because the backend matches the embedded content against the challenge.
  Switching to detached silently breaks `_signed_data_matches`.
- **The sidecar image is an operator prerequisite**, not something you can pull. It is
  profile-gated (`profiles: ["eimzo"]`) with a deliberately unresolvable placeholder
  image, so a plain `docker compose up` never needs it and the API degrades to 503.
- **Challenges are single-use and scoped to (company, account).** `getdel` in Redis.
  Signing the same challenge twice is a 400, which makes a retry loop look like an
  auth bug.

## Troubleshooting

| Symptom | Cause → fix |
|---|---|
| `socket closed (code 1006)` | Module not running → `open -a E-IMZO` (macOS). Confirm with `doctor`. |
| `timeout after 15000ms` | A native dialog is waiting on screen, or you called `generate_keypair`. |
| `certificates NONE` | macOS: the key is not on a mounted volume named `DSKEYS`. See "Get a real test key". |
| `API-key для домена null недействителен` | No apikey handshake this module session. The driver does it automatically — if you see it, you called CAPIWS by hand. |
| `Диск не найден` | You passed a `disk` that `list_disks` didn't return. Only its exact strings work. |
| ckc.html stuck on «Ждите ...» | No hardware token. Use `registrator/public/pfx.html`. |
| `HTTP 500`, empty log | `RUN_MIGRATIONS_ON_STARTUP=true` ate the handlers. Restart with it `false`. |
| `HTTP 500` on verify, log shows `botocore` | MinIO/S3 not reachable or bucket missing. |
| `Fernet key must be 32 url-safe base64-encoded bytes` | `VERIFICATION_ENC_KEY` is not a Fernet key. |
| `HTTP 400 challenge_expired` | Challenge consumed or >300 s old. Mint a fresh one per attempt. |
| `HTTP 503 eimzo_unavailable` | Sidecar down or breaker open. Expected without the UNICON image — set `EIMZO_STUB=true` for dev. |
| Node `WebSocket is not defined` | Node < 22. Use ≥ 22 (verified on v24.11.1). |
