# Deal Lifecycle — фундамент внешних интеграций

Версия 1.0 · 27.07.2026 · Основано на веб-исследовании официальных источников (июль 2026).
Дополняет `TZ.md` §3.4 (блок D). Каждый провайдер строится по паттерну R3-шлюза:
`backend/app/integrations/<provider>/` (typed-клиент, circuit breaker, `integration_call_log`,
`ProviderUnavailable`, режим `stub|live` за runtime-настройкой).

Легенда: ✅ подтверждено первоисточником · ⚠️ требует проверки у контрагента.

## 1. Didox — электронный документооборот (контракты, ЭСФ)

**Статус: лучшая готовность из всех провайдеров — публичная партнёрская API-документация.**

### Факты ✅
- Оператор: ООО «DIDOX TECH» (ИНН 310529901), крупнейший частный ЭДО-оператор (~350 тыс. компаний).
- Документация: **api-docs.didox.uz** (разделы `integrators-*`). Тест: `https://testapi3.didox.uz/`, прод: `https://api-partners.didox.uz/`. Канал изменений: t.me/didoxapiupdates.
- **Аутентификация двухуровневая:** заголовок `Partner-Authorization: <PARTNER_TOKEN>` на каждом запросе (токен выдаёт аккаунт-менеджер, t.me/Didox_account — оффлайн-онбординг) + пользовательский `user-key` (UUID, TTL 360 мин), получаемый по ЭЦП: `POST /v1/auth/{taxId}/token/{locale}` c PKCS7-подписью ИНН + timestamp.
- **Подпись остаётся у клиента:** PKCS7 создаётся локальным E-IMZO (`wss://127.0.0.1:64443` — тот же флоу, что наш R3 `features/eimzo-sign`); Didox добавляет TSA-метку через `POST /v1/dsvs/timestamp` и доставляет документ. Didox НЕ подписывает за пользователя.
- **Договоры — два типа:** «Договор НК» (юридически значимый, синхронизируется с роуминговым центром my.soliq.uz; структура `ContractDoc + Owner + Clients[] + Parts[] + Products[]`) и «Произвольный документ» subtype=договор (любой PDF ≤10 МБ, живёт только внутри Didox, в роуминг не уходит). **Для Deal Lifecycle используем «Договор НК».**
- Ключевые вызовы: создание `POST /v1/documents/:docType/create/{locale}`; подписание `POST /v1/documents/:docId/sign` `{signature: timeStampTokenB64}` (отправка контрагенту = факт подписания); входящий: `GET .../documentBase64` → своя подпись → `POST /v1/dsvs/signature/join` → sign; отказ `POST /v1/documents/:docId/tosign` (action) → `/reject`; **доказательная копия** `GET /v1/documents/:id/archive` (подписи+PDF+JSON, URL живёт 5 мин).
- Статусы: `0` черновик, `1` ждёт подписи партнёра, `2` ждёт вашей подписи, `3` подписан, `4` отказ, `50` аннулирован НК и др.
- **Webhooks в публичных доках отсутствуют** — только polling `GET /v2/documents` (есть фильтры `dateFromUpdated/dateToUpdated` — паттерн инкрементального опроса).
- Роуминг между 27 операторами ЭДО (rouming.uz): контрагент может обслуживаться у любого оператора — одной интеграции с Didox достаточно.

### Контракт нашего адаптера — `integrations/didox/`
```
DidoxClient:
  auth_user(tax_id, pkcs7_of_inn) -> user_key            # TTL 360 мин, кэш в Redis
  create_contract(user_key, contract_doc) -> doc_id       # «Договор НК» из наших variables
  timestamp(pkcs7) -> time_stamp_token_b64                # /v1/dsvs/timestamp
  sign(user_key, doc_id, time_stamp_token_b64) -> None
  join_signatures(sig1, sig2) -> pkcs7_b64                # входящая сторона
  get_document(user_key, doc_id) -> DidoxDocument          # статус, json, toSign
  list_updated(user_key, since) -> list[DidoxDocument]     # инкрементальный polling
  fetch_archive(user_key, doc_id) -> bytes                 # → S3 evidence (sha256)
```
- Celery-задача `poll_didox_statuses` (очередь интеграций, каждые N минут, настройка) — двигает `Contract`/`Deal` по статусам; идемпотентна.
- Portal: подписание — существующий `features/eimzo-sign` + новый шаг timestamp; UX «Didox за кадром» (пользователь не покидает платформу).
- Stub-режим: signing-провайдер `eimzo` (наш R3-контур) — уже работает.

### Prerequisite оператора / открытые вопросы ⚠️
1. Договор + Partner-token у аккаунт-менеджера (есть тест-контур — начать с testapi3).
2. Есть ли webhooks для партнёров (в доках нет — спросить)?
3. Тарифы партнёрства (публичны только пользовательские: 350–800 сум/документ).
4. SSO API (бесшовный вход) — условия.

## 2. Escrow-банк — платёжный контур сделки

**Статус: API будет предоставлен банком-партнёром (подтверждено заказчиком); проектируем
контракт адаптера сейчас, живём в stub до получения.**

### Правовой контекст ✅
- Общего института эскроу в ГК РУз пока нет; вводится секторно: **УП-246 от 10.12.2025** — с 01.04.2026 недвижимость/авто только через эскроу-счета; законопроект о долевом строительстве (июнь 2026) содержит правила эскроу; новая редакция ГК (проект) вводит условное депонирование.
- Для B2B-товарной сделки эскроу сегодня = **договорный банковский продукт** (трёхсторонний договор, банк-агент). ⚠️ Конструкцию договора валидировать с юристом (в т.ч. риски статуса «платёжной организации» при агентской схеме).
- **ПП-359 от 27.11.2025**: open banking в РУз обязателен к 01.09.2026 — банки строят API-инфраструктуру прямо сейчас; момент для переговоров удачный.
- Банки с готовыми эскроу-продуктами (по УП-246): **Kapitalbank** (запуск 25.06.2026), **NBU**. API-открытые кандидаты: Kapitalbank/Uzum, **Anorbank** («Anor API»: холдирование, счета, сплиты), TBC UZ.
- Карточные агрегаторы (Payme/Click/Atmos/Multicard) — C2B-эквайринг, для платежей юрлицо→юрлицо **не подходят**. Реальный рельс: платёжное поручение по счёту; для крупных сделок существует законный «деньги против документов» инструмент — **аккредитив в UZS** (Положение ЦБ № 3229).
- Синергия с Didox: платёж юрлица привязан к циклу ЭСФ — **подтверждение ЭСФ/акта покупателем — естественный триггер релиза** средств.

### Контракт нашего адаптера — `integrations/escrow/`
Проектируем от нашей доменной модели (банковский API мапится позже):
```
EscrowClient:
  open_escrow(deal_ref, amount, currency, buyer, seller) -> EscrowRef   # реквизиты для оплаты
  get_status(escrow_ref) -> EscrowStatus   # pending|funded|released|refunded
  request_release(escrow_ref, instruction) -> None    # по подтверждению доставки
  request_refund(escrow_ref, reason) -> None          # спор/отмена
# +入 webhook-inbox `provider_events` (идемпотентность по provider+external_id)
# + fallback-polling задача (как у Didox), т.к. форма уведомлений банка неизвестна
```
- Статусная машина `EscrowPayment` (`pending → funded → released/refunded`) одинакова в stub и live; Deal двигается ТОЛЬКО по ней.
- Stub: оператор в дашборде отмечает `funded/released/refunded` (двойное подтверждение + причина + audit).
- В `escrow_payments` не храним реквизиты счетов — только `provider_ref` банка.

### Prerequisite оператора / открытые вопросы ⚠️
1. Выбор банка + договор; получить спецификацию API (форматы, уведомления: webhook или host-to-host/опрос).
2. Юрвалидация трёхстороннего договора эскроу для B2B-товарной сделки.
3. Комиссии, сроки зачисления/релиза, лимиты; поведение при частичной оплате.
4. Валюта: UZS (мультивалютность — отдельный вопрос при экспортных сделках).

## 3. Гос-реестры — автопроверка компаний и лицензий

**Статус: официальный realtime-API для частных компаний — только через ПЦД (переговорный
трек); до него — E-IMZO (наш R3, уже работает) + полуавтоматические открытые сервисы.**

### Факты ✅
- **ПЦД (Платформа цифровых данных)** при Центре цифрового правительства (Минцифры) — единственный официальный канал API-доступа частных организаций к госреестрам (150+ подключённых организаций). Процесс: заявка → регистрация своей ИС в реестре персональных данных (Минюст) → сертификация кибербезопасности. **Порядок нормативно не формализован, критерии непрозрачны** — известны многолетние отказы без объяснений. Административная поддержка проекта — ключевой рычаг именно здесь.
- Доступно уже сейчас (без ПЦД):
  - **Реестр плательщиков НДС** — открытый поиск по ИНН на my.soliq.uz (статус свидетельства);
  - **Поиск лицензий по ИНН** — сервис ЕПИГУ (КИС «Лицензия», license.gov.uz), бесплатный;
  - **Налоговая задолженность** — публично, но за captcha (автоматизация не предусмотрена);
  - **ЕГРПО** (registr.stat.uz): статус, руководитель, ОКЭД, адрес — через OneID;
  - **data.egov.uz** — датасеты с API по ключу (JSON/XML), но статические — для обогащения, не для realtime.
- **OneID** (id.egov.uz) — гос-SSO с идентификацией юрлиц (связка ПИНФЛ↔ИНН); для частных платформ платно по договору (ПКМ-679), OAuth2-подобный поток. Кандидат на дополнительный канал входа/верификации.
- Агрегаторы (orginfo.uz, myorg.uz) — неофициальные, без гарантий и публичного API.

### Контракт нашего адаптера — `integrations/gov_registry/`
```
GovRegistryClient:
  lookup_company(inn) -> CompanySnapshot      # имя, статус, директор, ОКЭД, адрес, дата рег.
  lookup_licenses(inn) -> list[LicenseSnapshot]
  lookup_vat(inn) -> VatSnapshot              # статус свидетельства НДС
# каждый ответ сохраняется immutable snapshot-ом (evidence) + upsert авто-чеков VerificationCase
# (method: registry); недоступность → чек `unavailable`, ручной путь не блокируется (инвариант R1)
```
- Stub: текущая R1-верификация (стафф + документы) + R3 E-IMZO (сильнейший доступный механизм: подпись = контроль над компанией, ИНН/название/директор из сертификата).
- Промежуточный полуавтомат (опционально, до ПЦД): операторская кнопка «проверить в реестре» с ручным вводом результата из открытых сервисов + сохранением скриншота как evidence.

### Prerequisite оператора / открытые вопросы ⚠️
1. Заявка в ПЦД (через административный ресурс проекта): какие именно API из каталога ПЦД доступны (ЕГРПО? КИС «Лицензия»? НДС-реестр?), SLA, тарифы.
2. OneID: договор, состав полей по юрлицу, тариф (ПКМ-679).
3. Текст ПП-257 (июль 2026, перечень ГИС 2026–2028) — на lex.uz: там единые реестры физ/юрлиц.

## 4. Реестр опасной химии — комплаенс публикации

**Статус: машиночитаемого гос-реестра НЕ СУЩЕСТВУЕТ. Источник истины — наш собственный
справочник `substances`, оцифрованный из официальных перечней (ПКМ). Это не времянка,
а архитектурное решение.**

### Правовая карта ✅
Закона «О химической безопасности» пока нет (законопроект по УП-224 от 24.12.2024;
НРОХВ chemical-safety.uz заявлен, но пуст/не подтверждён). Действуют **четыре отдельных
режима**, каждый со своим перечнем:

| Режим | Акт | Что внутри | Требование |
|---|---|---|---|
| **Прекурсоры (Список IV)** | ПКМ № 330 от 12.11.2015 (+ПКМ 878/2018), 29 позиций | ацетон ≥60%, толуол ≥70%, МЭК ≥80%, соляная к-та ≥15%, серная к-та ≥45%, перманганат калия ≥45%, ангидрид уксусной к-ты (без порога)… | Лицензия (ПКМ № 315, срочная, система Минздрава); ВЭД — сертификат на каждую партию (до 30 раб. дней, согласование СГБ/МВД). Изъятие: ниже пороговой концентрации И ≤12 кг(л)/год — вне контроля |
| **Взрывчатые/ядовитые** | ПКМ № 782 от 02.10.2018 + ПКМ № 397 от 30.06.2025 | взрывчатые, ядовитые в-ва, классы токсичности I–III | Лицензия Комитета пром/рад/ядерной безопасности, с 01.08.2025 — согласование МЧС |
| **Сильнодействующие** | ПКМ № 818 от 27.09.2019 | ~100+ позиций с «крупными размерами» и ТН ВЭД | отдельный режим оборота |
| **Импорт/экспорт опасной продукции** | ПКМ № 916 от 30.12.2024 (действ. с 11.04.2025) | 3 перечня по ТН ВЭД: запрещённые к ввозу; запрещённые СЗР/СОЗ; госрегулируемые + экосертификация | запрет либо экологическая сертификация |

Ключевые следствия для модели данных:
- **Официальные перечни используют наименования + коды ТН ВЭД, НЕ CAS** — юридический
  идентификатор у нас = ТН ВЭД/HS-код + наименование; CAS — вторичный (для AI-матчинга
  и международных SDS).
- **Регулирование зависит от концентрации** (ацетон 60%, кислота 15%…) и годового объёма —
  в `substances` нужны поля `threshold_concentration_pct` и `exemption_annual_limit`;
  проверка при публикации учитывает концентрацию из описания оффера.
- `regulation_regime` (precursor_list_iv | explosive_toxic | strong_acting | pkm916_import)
  вместо/рядом с абстрактной «категорией лицензии» — у каждого режима свой лицензиар и документы.
- **Полимеры (PP, PE, PVC, PET, PS) не входят ни в один перечень — свободный оборот** ✅.
  Оговорки: отходы пластмасс (ТН ВЭД 3915) — режим ПКМ 916; «новые» полимерные материалы
  (пищевой контакт) — токсиколого-гигиеническая оценка по ЗРУ-393.
- ГОСТ-классы опасности I–IV и GHS-гармонизированные ГОСТы (маркировка) — используются,
  но обязательного нацрегламента GHS нет.

### Контракт — `integrations/chem_registry/` (тонкий) + сид справочника
- Live-адаптер появится только если НРОХВ/ПЦД дадут API — интерфейс `lookup_substance(hs_code|name)`
  закладываем, реализация надолго stub.
- Основная работа — **сид `substances`**: оцифровка Списка IV (29 позиций, с порогами),
  ПКМ 818, ПКМ 782-категорий и ПКМ 916-перечней из lex.uz → `app/seed/seed_substances.py`
  (идемпотентный, версионируемый — правка перечня = новая ревизия сида + миграционная запись).
- Мониторинг: принятие закона «О химической безопасности» → возможен единый реестр → ревизия.

### Prerequisite оператора / открытые вопросы ⚠️
1. Юрист: подтвердить перечни и текущие редакции (приложения к ПКМ на lex.uz местами не отдаются программно).
2. Статус НРОХВ (chemical-safety.uz): оператор, наполненность, планы API.
3. Позиция платформы: показываем ли вообще офферы веществ Списка IV без подтверждённой лицензии (рекомендация: нет — «прекурсорный» риск репутационно токсичен).

## 5. Сводный план подключения

| Провайдер | Можно строить сейчас | Блокер live | Оценка после получения доступа |
|---|---|---|---|
| Didox | адаптер + флоу целиком против testapi3 (после partner-token) | договор с Didox | маппинг уже написанного: дни |
| Escrow-банк | доменная модель + stub + generic-адаптер | договор с банком + спецификация API (обещан) | 3–7 дней маппинга + интеграционное тестирование |
| Гос-реестры | интерфейсы + snapshot-механика + полуавтомат | доступ к ПЦД (админресурс) / OneID-договор | 3–7 дней на реестр |
| Реестр химии | **всё сейчас** (свой справочник из ПКМ) | нет (live-API не существует) | — |

Общие правила (для всех): вызовы на выделенной Celery-очереди; timeouts + circuit breaker;
`integration_call_log`; immutable snapshots в evidence; недоступность провайдера деградирует
в `unavailable`/ручной путь и никогда не блокирует Deal-пайплайн; `<provider>_mode` —
runtime-настройка.
