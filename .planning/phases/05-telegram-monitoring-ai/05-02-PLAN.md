<objective>
Build the net-new long-lived Telegram monitoring userbot (Telethon/MTProto) as a SEPARATE process from api/worker/beat, wire the previously-pending `telegram_channel` adapter into the existing SourceAdapter registry, and add the Redis-heartbeat liveness path with a deduped admin alert on silence >5 min. This delivers ROADMAP SC#1: a long-lived userbot that subscribes to enabled `telegram_channel` sources, re-reads the channel list every ~10 min without restart, writes new messages to `raw_items`, and emits a heartbeat.

Messages land in `raw_items` with `parse_status='pending'` through the EXISTING immutable `save_raw_items` dedupe path — they are then picked up by the LLM parse orchestrator built in 05-04. This plan stops at `raw_items`; it does not call the LLM.

Purpose: Real channel messages must flow into the same immutable pipeline the rest of the system uses, with no single-process coupling to the API and with a liveness signal so the team knows when monitoring is down (the FloodWaitError / account-restriction risk from AI-SPEC §1b is customer-borne but must be observable).

Output: `userbot/` package + its compose service, a live `telegram_channel` adapter, and the heartbeat/health path.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public Telegram channel → userbot → raw_items | Attacker-controllable message content crosses into the immutable store (text persisted verbatim; not yet sent to LLM) |
| Customer Telegram account/session string → userbot process | Long-lived credential; compromise grants account access |
| userbot → Redis heartbeat / Postgres | Liveness + persistence boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05 | Information disclosure | TG_SESSION_STRING / TG_API_HASH | mitigate | Env-only via settings; never a source literal; .env.example marks `[SECRET]`; not committed; grep gate asserts no hardcoded session string |
| T-05-06 | Denial of service | userbot fetch rate → account restriction | mitigate | FloodWaitError caught + sleep e.seconds (polite rate); restriction risk customer-borne (AI-SPEC §1b) but observable via heartbeat alert |
| T-05-07 | Tampering | malformed/hostile channel message | mitigate | Per-message try/except isolates failures; empty/media-only skipped; content persisted verbatim to immutable raw_items (no parsing here — injection defense is in 05-03 at the LLM boundary) |
| T-05-08 | Denial of service | userbot process death (silent monitoring outage) | mitigate | Redis heartbeat + check_userbot_health */5 + deduped userbot_silent alert; restart: unless-stopped |
| T-05-09 | Spoofing | forged enable of an unintended channel | mitigate | channel_registry only honors sources with last_test_ok_at IS NOT NULL (enable-gate invariant from Phase 4 carries forward) |
</threat_model>
