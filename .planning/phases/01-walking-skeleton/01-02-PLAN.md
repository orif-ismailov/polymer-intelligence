<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration runner → database | DDL execution with elevated privileges; concurrent runners must be serialized |
| seed data files → database | Static repo data written to reference tables |
| application code → ORM → SQL | Future query paths must not allow injection (models define the contract here) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | concurrent migrations | mitigate | api entrypoint wraps `alembic upgrade head` in a `pg_advisory_lock`; a second concurrent api container blocks instead of racing the DDL |
| T-02-02 | Tampering / Integrity | schema drift from contract | mitigate | Migration is a verbatim reproduction of the locked DDL; acceptance asserts table/ENUM/view counts and key column types; schema changes only via new migration + DB-doc edit |
| T-02-03 | Information Disclosure | `/health` schema_version | accept | Exposing the alembic revision string is low-value; no credentials or row data leaked |
| T-02-SC | Tampering | alembic/seed deps | mitigate | Alembic + SQLAlchemy are part of the canonical locked stack (plan 01-01 pyproject); no new third-party packages introduced |
| T-02-04 | Elevation of Privilege | ORM SQL injection (future) | mitigate | Models use parameterized SQLAlchemy constructs; the raw `v_live_feed` SQL is static (no user input); seed uses parameterized upserts, not string-built SQL |
</threat_model>
